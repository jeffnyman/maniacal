What is done, what comes next, and where each piece comes from. Source references are to the
ScummVM checkout next to this repository (`scummvm/engines/scumm`); `docs/...` is the documentation
in this repository; [docs/building-an-interpreter.md](docs/building-an-interpreter.md) explains the layers below.

## Design

ScummVM builds Maniac Mansion's engine as a chain of subclasses:
`ScummEngine_v0 : v2 : v3old : v3 : v4 : v5 : ScummEngine`. Much of what Maniac Mansion runs on
lives in the V5 and base classes, mixed with code for later games (iMUSE, HE, SMUSH, AKOS,
256 colors). Maniacal does not port that chain. It has one flat `ScummEngine` with the version (0, 1
or 2) as data, and it takes from each ScummVM function only the branches that `_game.version <= 2`
and `GID_MANIAC` reach. Where V0 genuinely differs (scripts, verbs, actor walking), it gets its own
class, as Daventry did for preAGI.

The three versions split the work like this:

| | V0 (C64) | V1 (DOS 1987) | V2 (DOS 1988) |
|---|---|---|---|
| Scripts | `script_v0.cpp` | `script_v2.cpp` | `script_v2.cpp` |
| Index | inside the disk image | `readClassicIndexFile` | `readEnhancedIndexFile` |
| Room graphics | `GdiV1` (C64 character tiles) | `GdiV1` | `GdiV2` |
| Costumes | `V0CostumeLoader` / `V0CostumeRenderer` | `ClassicCostume*`, version 1 branches | `ClassicCostume*` |
| Sound | `Player_SID` | `Player_V1` (PC speaker, PCjr) | `Player_V2` (PC speaker, PCjr) |
| Verbs | V0 sentence UI (`ScummEngine_v0::checkExecVerbs`) | V2 verbs | V2 verbs |

So the order is V2 first, because ScummVM's support for it is the best exercised and it has the
fewest special cases. V1 follows by swapping in the `GdiV1` graphics and V1 costumes under the same
script VM. V0 comes last, with its own scripts and verbs, which then reuse V1's graphics.

Every phase ends with a headless check, as in Daventry: a screenshot of a known room, or a scripted
run of clicks that reaches a known state.

## Phase 1: resources (done)

Both DOS releases, in `Maniacal.Scumm.Resources`, `Rooms`, `Graphics` and `Costumes`:

- **Detection.** ScummVM's 40 Maniac Mansion MD5 rows (generated by `tools/port_md5_table.py`), the
  variant-to-version table of `detection_tables.h`, and identification of the loose-file releases by
  `00.LFL` / `00.MAN`. V1 and V2 English DOS are identified.
- **Files and indexes.** `file.cpp`, `resource.cpp`, `resource_v2.cpp`: the XOR-encoded `.LFL`
  files (`LflFile`), both index formats (`ResourceIndex`: object owners and states, and where every
  room, costume, script and sound is), and loading a resource by its size word (`ResourceLoader`).
- **Rooms.** `room.cpp`, `object.cpp`, `boxes.cpp` (reading): the room header, the objects' code blocks
  (number, geometry, parent, walk-to point, preposition, name, verb table), the walkboxes and box
  matrix, the entry and exit scripts, and the sounds and scripts loaded with each room.
- **Pictures.** `gfx.cpp`, `palette.cpp`: room pictures and masks (`V2Bitmap`, `V1Bitmap`), object images, and
  drawing a room with its objects as `drawRoomObjects` does (`RoomRenderer`), in EGA colors.
- **Costumes.** `costume.cpp`: the classic costume format (`0x58`, V2) and its C64-derived variant (`0x57`, V1):
  animations, limb command runs, cels, and figures built from them (`Costume`, `CostumeRenderer`),
  with V2's start offset of (-72, -100) from `drawCostume` and V1's actor color tables.
- **No charset files.** V1 and V2 fonts are built into the engine (`ScummEngine_v2::loadCharset` is a
  stub); the font is ported in Phase 2.
- **Tools.** `maniacal <folder> --room N [--objects none|initial|all] [--mask]` and
  `maniacal <folder> --costume N` write rooms and costume sheets as PNGs (`--zoom N` to enlarge).
- **Checked.** Every room, object image and costume of both releases decodes; pictures match the
  room maps by eye and an independent decoder by hash; the room layouts end exactly where the next
  part begins; every room file is a chain of sized resources, and the index entries that point at
  real resources are counted and pinned in the tests.

## Phase 2: drawing, V2 then V1 (done)

- **V2 pictures.** The picture and mask decoder (`GdiV2::prepareDrawBitmap`, `generateStripTable`) as
  `V2Bitmap`, and the EGA palette. Every V2 room decodes, ending exactly where its object images begin.
- **V1 pictures.** The tile decoder (`GdiV1::roomChanged`, `decodeV1Gfx`, `drawStripV1Background`,
  `drawStripV1Mask`) as `V1Bitmap`, with the Maniac Mansion EGA row of `setV1ColorTable`. Every V1
  room decodes, ending exactly where its object images begin.
- **Palettes.** V1 and V2 both use the EGA palette (`palette.cpp`, `resetPalette`); the C64's came
  with V0 (Phase 5).
- **Actors on the room.** `RoomView`: the position offsets of `Actor_v2::prepareDrawActorCostume`
  (+8 in V2, +16 facing left), V1's one-line drop, and clipping by the room mask when the actor's
  walkbox has one (ScummVM's two mask planes: plane 0 empty, plane 1 the room's). Dark rooms and
  drawing actors back to front came with the interpreter (Phase 3).
- **The font.** The built-in English font (`CharsetRendererV2`, `charset-fontdata.cpp`, generated by
  `tools/port_fonts.py`), with V1's own apostrophe, and drawing text with it (`Font`). Other languages'
  replacement glyphs can be ported the same way when there is data to test them.
- **The camera.** `camera.cpp` (`Camera`): the view centre in pixels, 8 pixels a step, following
  an actor past view columns 10 and 30, panning, and the script limits that `startScene` resets on each room.
- **The screen.** The layout of `initScreens` (`ScreenLayout`), and
  `maniacal <folder> --view N [--camera X] [--actor costume,x,y[,direction]]...`, which writes the
  320x200 screen with the room and standing actors.
- **Checked.** Headless screenshots of rooms with actors in them, and later, through saves, the
  same screens as ScummVM 2.7.0's (Phases 3 and 5).

## Phase 3: the interpreter, V2 and V1 (done)

- **Decoding.** `Maniacal.Scumm.Scripts`: the opcode table of `ScummEngine_v2::setupOpcodes`
  (generated by `tools/port_opcodes.py`) and the operand layout of each of its 107 handlers
  (`ScriptDecoder`), with decoding along every path execution can take. Every global, room and
  object script of both releases decodes, with jumps landing on instruction boundaries; the only
  leftover bytes are 20 after V2 script 59. `maniacal <folder> --script N` and `--room-scripts N`
  print the disassembly.
- **The script engine.** `ScriptEngine`: 80 slots, nested starts, `runAllScripts`, delays,
  freezing, the user state, cutscenes and overrides, variables (with the 14-16 redirection and the
  exit-key remap), bit variables, object states and owners, and the variable, arithmetic,
  condition, jump and script-control instructions. Every other instruction goes to an
  `IScriptHost` with its operands evaluated. `maniacal <folder> --run [steps]` runs the boot script
  headless and lists what the scripts asked of the world: both releases reach the kid selection.
- **The world.** `GameWorld`: `loadRoom` as `startScene` does it for these versions
  (leave and kill the room's scripts, the exit script, the room variable, the camera limits, the entry
  script, then script 5), `setCameraAt`, `panCameraTo`, the camera limits of `roomOps`, and `lights`;
  a main-loop step (delays, scripts, camera); and the screen drawn from the object states.
  `maniacal <folder> --run [steps] --screenshot file.png` shows the title screen in both releases.
- **Actors.** Without walking (`Actor`, `CostumeState`): the per-limb costume state of
  `costumeDecodeData` and `increaseAnim`; `putActor`, `showActor`, `hideActor`, `setActorCostume`,
  `animateActor`, `setDirection` and `animateCostume`; V1's default costumes and talk colors;
  `actorOps`, the put and query instructions, `actorFollowCamera` and `loadRoomWithEgo`; drawing
  the actors in the room back to front, in their palette under the current lights. With the kid
  selection stood in for by `--set` and the intro skipped by `--skip`, both releases reach the start
  of the game with the three kids on the driveway.
- **Walking.** `BoxGeometry`, `Actor`: the box geometry of `boxes.cpp`, V2's
  `adjustXYToBeInBox` and `adjustActorPos`, `startWalkActor`, `walkActor` leg by leg through the box
  matrix, `calcMovementFactor` and `actorWalkStep`, turning a quarter at a time
  (`updateActorDirection`, `remapDirection`), and the box flags `setBoxFlags` changes. The walk,
  face, wait and distance instructions; `drawObject` without moving; and the per-step engine
  variables of `scummLoop_updateScummVars` (the camera column). The intro plays through in both
  releases, from the meteor to the kids on the driveway.
- **Text.** `MessageLine`: `decodeParseString`, `convertMessageToString` (numbers, verb and
  object names, text in variables), `actorTalk`, `displayDialog` with its wrap, new-line, wait and
  keep escapes, the talk delay of 60 ticks and 6 a character, `stopTalk` and the talk frames;
  `print`, `printEgo` and `waitForMessage`; and the main loop's tick count and message variable.
  The intro's text and the kids' first lines show on the message line in both releases.
- **Verbs, sentences and input.** `VerbArea`, `GameWorld.Interface`: `o2_verbOps`,
  `drawVerb`, `redrawVerbs`, `verbMouseOver` and `findVerbAtPos`; the sentence queue of
  `o2_doSentence`, `checkAndRunSentenceScript`, `waitForSentence` and `drawSentence` with
  prepositions; the inventory (`pickupObject`, `setOwnerOf`, `redrawV2Inventory`, its scrolling and
  highlight boxes); `findObject`, `actorFromPos` and `getObjPreposition`; `processInput` and
  `ScummEngine_v2::checkExecVerbs` with the input script, the verb and inventory keys, and Escape,
  F4 or the right button for skipping cutscenes; the end of a cutscene giving the camera back to
  the kid; and the V2 crosshair cursor. `ScummEngine` runs it all on the host, a step every
  `VAR_TIMER_NEXT` sixtieths of a second. Both releases play from the title through the kid
  selection (by clicking) and the intro to the driveway, out to the front of the house, and the
  key under the door mat goes into the inventory, headless and in the SDL window.
- **Objects and lights.** `o2_drawObject` moving an object and its walk-to point for as long as
  the room is loaded, `setObjectName` and the new names `getObjOrActorName` gives first,
  `getClosestObjActor`, and dark rooms: black where the room lights are off (`clear8Col`), with
  the flashlight of `o2_lights` and `drawFlashlight`, its corners rounded by the version 1 and 2
  curves, lighting the room around the mouse. Rooms 5, 8, 9, 15, 22 and 23 start dark.
- **Into the house**, checked against ScummVM 2.7.0 by loading the same saves in both: the hall,
  the kitchen, Edna catching a kid and locking him in the dungeon, the dungeon's brick and door, the
  gargoyle that holds a door open while the kid who pulled it stands still, and the basement dark
  and lit. Every opcode the game's scripts use has a handler. Two fixes came of it: a load from
  outside the save screen now goes through the save room inside a cutscene and back, as ScummVM's
  does after a launcher load (`ScummEngine_v3::scummLoop_handleSaveLoad`, with
  `terminateSaveMenuScript` for a save made in the save room), which puts the camera on the kid;
  and `o2_restart` starts the game over (`ScummEngine::restart`).
- **ScummVM 2.7.0 and now.** Where ScummVM 2.7.0 and the current ScummVM differ, Maniacal follows
  the current one: after a user state change the sentence line is drawn again (`runInventoryScriptEx`), and only version 1
  puts back the camera mode a cutscene began with (`o2_endCutscene`).

Where it comes from:

- `script.cpp`: script slots, `runScript`, `runObjectScript`, `runEntryScript`/`runExitScript`,
  cutscenes, `stopScript`, freeze and unfreeze, the bit variables.
- `script_v2.cpp`: the V2 opcode table (also used by V1) and every handler.
- `vars.cpp`: `ScummEngine_v2::setupScummVars` and `resetScummVars`.
- `scumm.cpp`: the main loop (`scummLoop` and what it calls each frame), `resetScumm`, timing.
- `actor.cpp`: `Actor`, `Actor_v3` and `Actor_v2`, with walking, facing, animation and talking.
- `boxes.cpp`: walkboxes, the box matrix and path finding, version 2 branches.
- `verbs.cpp`: `initV2MouseOver`, `checkV2MouseOver`, `redrawV2Inventory`, `checkExecVerbs`.
- `string.cpp`: messages, `drawSentence`, talk text.
- `input.cpp`: mouse and keyboard, `ScummEngine_v2::processKeyboard`.
- `docs/scripts`: the C64 scripts. The logic is the same game, but DOS renumbers scripts,
  variables and objects (see `docs/scripts/README.md`, "The DOS releases"), so a V0-to-DOS number
  map comes before naming variables from its tables.

## Phase 4: sound, saves and options, V2 and V1 (done)

- **Sound.** `Maniacal.Scumm.Sound`: `Player_V2Base` and `Player_V2`, the four-channel
  sequencer of version 2 with its hulls and modulation curves (tables generated by
  `tools/port_sound_tables.py`); `Player_V1`, the chunked effects of version 1; the PC speaker's
  and PCjr's synthesis, the PCjr by default as ScummVM chooses it (`--speaker` for the other);
  the queue of `sound.cpp` with `startSound`, `startMusic`, `stopSound`, `stopMusic`,
  `isSoundRunning`, `VAR_LAST_SOUND` and the music timer. With it, the main loop's clock is the
  original's: steps last `VAR_TIMER_NEXT` ticks of 4 quarter-frames at 1193182 / 5041 Hz in
  version 2, and in version 1 a multiple of 3 ticks at 12 quarter-frames a tick of the 18.2 Hz
  timer (`setTimerAndShakeFrequency`, `ScummEngine::go`). `--run ... --wav file.wav` records a run.
- **Saves.** `Maniacal.Scumm.Saves`: ScummVM's save format for these versions, field for field
  (`ScummEngine::saveLoadWithSerializer`, `ScummEngine_v2::saveLoadWithSerializer`, the actor,
  script, object, verb, sentence and string serializers, the resources, gzip, the header and the
  information section), written in save version 108 (ScummVM 2.7's) by default or 124, and read
  from 108 to 124; the game's own save screen (`o4_saveLoadGame`), saving mid-script as ScummVM
  does and, after a load, carrying on after the instruction or booting and loading again when the
  save was made outside the save room. Checked against ScummVM 2.7.0: a save made here loads
  there; a save-screen save made here, loaded there, is saved again by ScummVM and loads back
  here; and the two saves of the same moment differ only in the mouse and a few ticks of time.
- **Copy protection.** `GAMEOPTION_COPY_PROTECTION`: as in ScummVM, it is bypassed by
  default, `getState` keeping both sides of the steel security door (objects 182 and 193) open so
  its code is never asked for; `--copy-protection` keeps it.

## Phase 5: Commodore 64 (V0) (done)

### The C64

- **Disk images.** `C64DiskImage`, from `ScummDiskImage`: the two disks seen as the DOS
  releases' loose files, the index rebuilt as `00.LFL` (signature `0x0132`) and each room's
  resources gathered from its track and sector into `NN.LFL`, encoded as the DOS files are, with the
  per-room resource counts and track starts generated by `tools/port_disk_tables.py`. The disks are
  found by ScummVM's names (`maniac1.d64`, `maniac2.d64`, `maniacdemo.d64`) or, failing those, by
  the words two disk images start with. The version 0 index (`readClassicIndexFile`: 256 objects,
  25 costumes, 160 scripts, 70 sounds, fewer in the demo) and detection by the MD5 of the rebuilt
  index, as `openDiskImage` does: the copy here is ScummVM's English C64 row. Checked: every room
  file is an exact chain of sized resources, and the index entries that point at real resources
  are counted and pinned, as for DOS.
- **Rooms.** The header is version 1's; objects (`ScummEngine_v0::resetRoomObject`) have their
  fields a byte earlier, the name's offset at 13 and the verbs from 14, a type in the number's high
  byte (0 for objects with an owner and state, 1 for those that are part of the room), and an
  image offset equal to the first code block's when they have none (`resetRoomObjects`). The
  walkboxes are rectangles up to an 0xFF, corner boxes narrowing their top as
  `getBoxCoordinates` has it, followed by each box's neighbours rather than a matrix
  (`getBoxConnectionBase`, `getNextBox`; the C64's own search is `walkboxes/walkbox_dfs.asm`).
- **Pictures.** `GdiV1` draws them, in the C64's own color numbers and ScummVM's C64 palette
  (`tableC64Palette` and the rows of `setV1ColorTable`, generated with the EGA palette by
  `tools/port_palettes.py`). The layers come in another order, the mask map last. The mask
  characters' length word is 8 more than their data, as in version 1; the C64 decodes the whole
  length (`read_room_graphics` in `resources/room_loader.asm`), and its last tile is used, so
  Maniacal does too where ScummVM stops 8 bytes short. Checked: every room's picture ends where
  what follows it begins, the 250 object images that are their objects' own decode, and the front
  of the mansion and the hall look right by eye (no C64 screenshot to compare against yet).
- **Decoding.** The V0 scripts: the opcode table of `ScummEngine_v0::setupOpcodes` (generated
  with version 2's by `tools/port_opcodes.py`) and the operand layout of each of its 95 handlers.
  Version 0 reads a word operand as a byte (`fetchScriptWord`, `getVarOrDirectWord`) but a jump
  as a word; the state instructions take their object as a byte, or with bit 0x40 none, meaning
  the running sentence's object (`getActiveObject`); text is bytes to a zero, bit 7 a space
  after (`decodeParseString`). Every global, room and object script of the C64 release decodes
  along every path, jumps landing on instructions, with the 20 leftover bytes of V2 script 59 after
  C64 script 54; and every instruction offset in `docs/scripts/retail` (154 global scripts, 75
  room scripts, 434 objects' scripts) is one decoded here, but for the meteor, whose Pick up
  begins with another instruction in the copy here than in the listing's.
- **Booting.** The C64 boots to its kid selection. The engine's variables are numbered as each version
  numbers them (`EngineVariables`, from both `setupScummVars`), with none where a version has none,
  as ScummVM's `VAR_*` stay 0xFF: version 0 has nine, and keeps its lights in the engine
  (`getCurrentLights`, set by `o_lights`). Its own bit variables (`_bitVars`), the sentence's verb
  and objects the scripts read (`_cmdObject`), and the instructions the boot runs: `o_cutscene`
  and `o_endCutscene` with the mode and room they keep, `o_setMode` and the four modes as user
  states, `o_print` and `o_printEgo` with version 0's text (`decodeParseString`), and the
  resource instructions, which do nothing here. Objects that are part of a room have no state.
  `startScene` resets the sentence and runs script 5 in versions 1 and 2 only. The screen is
  `initScreens(9, 145)`, and a step 4 ticks at the C64's 240 quarter-frames a second (NTSC); the
  ticks for the C64's redraw time came later. Sounds went nowhere until the SID player was ported,
  as in ScummVM built without it.
- **Verbs and sentences.** The C64's, which its engine handles itself: the 15 verbs of
  `resetVerbs` (generated by `tools/port_v0_verbs.py`) in its colors, the sentence line and
  inventory a pixel right and down; `processInput` (F1 to F3 for the kids, Escape and the right
  button always skipping a cutscene); `checkExecVerbs` making the sentence from clicks, with the
  keypad mode's Push carried out at once; `verbExec`, `drawSentenceLine` with New kid's names,
  `switchActor`, `checkAndRunSentenceScript` with its pick-up first and walk first, and
  `runSentenceScript` with Give's default and script 3 for verbs no object answers;
  `o_doSentence`. Version 0's catch-all verb entry is What is, 0x0F (`getVerbEntrypoint`), so the
  portraits' What is scripts answer the keypad's Push. Objects carry their type in their number
  (`OBJECT_V0`), and only an actor-type number is an actor (`objIsActor`). Checked: the kids are
  picked by clicking, and START starts the intro, which stops at its first costume.
- **Costumes and actors.** `V0Costume` reads the format of
  `V0CostumeLoader::loadCostume`: 8 limbs, each with sequences of cels, and clips that each start a
  sequence on every limb, mirrored or not. `V0CostumeState` plays them (`costumeDecodeData`,
  `limbFrameCheck`, `increaseAnims`, each clip with its repeats) and `V0CostumeRenderer` draws them
  as `drawLimb` does, 2-wide pixels in the actor's own colors, generated with the actors' names,
  talk colors and talk flags by `tools/port_v0_actors.py`. `ActorV0` is `Actor_v0`: clips in
  place of frames (`animateActor`, `startAnimActor`, `setDirection`, `turnToDirection` turning at
  once), 2 for standing in `_moving`, the mouth's clips (`speakCheck`, opened and shut each frame by
  `processActors`, which animates the actors before drawing them and draws the plant first), and
  its own walking: the boxes on the way planned as it sets off (`walkBoxQueuePrepare`), a point in
  each next box (`walkboxFindTarget`), and a column or line a step that goes round a box's edge
  when it must (`walkActor`, `calcWalkDistances`, `actorWalkXCalculate`, `updateWalkbox`). Points
  are moved into the boxes from box 0 up, columns counting double, and off slanted boxes' diagonals
  (`adjustPosInBorderWalkbox`). The instructions: `o_animateActor`, `o_getActorMoving`,
  `o_setActorBitVar` and `o_getActorBitVar` (a frozen kid stops), `o_putActorAtObject`,
  `o_walkActorToObject`, `o_loadRoomWithEgo` and `o_getClosestActor`; the walk before a sentence
  is `walkToActorOrObject`'s. The game starts with Dave (`resetScummVars`), and verbs are drawn a
  pixel right and down, as `drawVerb` does on the C64. `--costume N` draws the C64's costumes too.
  Checked: every clip of every costume decodes; the intro plays to the mansion's drive, where Dave
  walks where the room is clicked and reads the sign, and the screen there looks right by eye.
- **Differences from ScummVM.** in a slanted box, `adjustPosInBorderWalkbox` makes every column up to
  160 on the diagonal 0, where the C64 keeps it and makes only a column past 160 0
  (`clamp_to_diagonal_edge` in `walkboxes/walkbox_snap.asm`); Maniacal follows the C64. The test
  for reaching the last box (`areBoxesNeighbors`) reads the neighbour lists from 4 bytes in, as
  ScummVM does; the C64 plans its routes another way (`walkboxes/walkbox_waypoint_planner.asm`).
- **The inventory.** `o_pickupObject`, `o_setOwnerOf` and `o_setObjectName`, 0 meaning
  the running sentence's object, the name's object typed by the opcode's bit 0x80; the inventory
  is cleared a pixel right and down, as `redrawV2Inventory` does on the C64. Every version 0
  instruction now has a handler. Checked: Dave goes from the street to the porch, pulls the door
  mat, picks up the key (which the inventory shows), unlocks the front door with it, which opens
  it, and walks into the hall.
- **Saves.** In ScummVM's format. Each actor saves `Actor_v0`'s fields after `Actor`'s, in
  place of version 2's step fields, and starts its clip again when loaded as
  `Actor_v0::saveLoadWithSerializer` does; the engine's mode, lights, sentence and walk follow
  version 2's fields (`ScummEngine_v0::saveLoadWithSerializer`), and a read before save version
  124 leaves room for them after the music engine's block. The bit variables, the cutscene's mode
  and room, the C64's palette and its boxes as `resetRoomSubBlocks` keeps them go in too; its actor
  names are the engine's, not resources. F5 opens the game's own save screen (script 2) and F7
  skips a cutscene (`ScummEngine_v2::processKeyboard`); a load from outside it in the save room ends
  the save screen (`ScummEngine_v0::terminateSaveMenuScript`). The cursor takes the C64's colors
  (`default_v0_cursor_colors`). A restart now puts the C64's actors back as well.
- **Saves checked against ScummVM 2.7.0.** A save made with the C64's save screen in the hall loads there
  from the launcher (its MD5 and version accepted, the save screen shown), and ScummVM writes it
  again; that save loads here into the hall with Dave where he was, and the two saves differ only
  in a script's delay and the talk delay (ScummVM saved a moment later), the mouse (ScummVM had
  none), the actors' clips (which its load starts again) and the cursor's colors, which are the
  DOS ones in 2.7.0 and the C64's in ScummVM now. The C64 was only checked through saves, which
  need no input, not by playing it there.
- **Sound.** `Sid` is ScummVM's SID emulator (`audio/softsynth/sid.cpp`, from reSID):
  three voices of a 24-bit oscillator, noise register and ADSR envelope, the combined waveforms of
  the 6581, its filter with the cutoff curve reSID's spline draws, and the C64's output stage,
  clocked at the NTSC rate and sampled; its tables come from `sid.cpp` and `wave6581.cpp` by
  `tools/port_sid_tables.py`. `PlayerSid` is `Player_SID`, ported from the C64 engine's own
  driver: songs on the three voices through the player's channel buffers, sounds that take voices,
  pulse widths and the filter by priority, a background sound stepped out of sight while it waits
  for a voice, ticked 60 times a second (`EmulatedChip::readBuffer`); its resource locking, which
  changes nothing, is left out. The players share a base (`MusicPlayer`, ScummVM's `MusicEngine`).
  Checked against ScummVM 2.7.0, recorded with SDL's disk audio driver from the same save: a sound
  came out sample for sample the same, and a later one, started at another point of the chip's
  frame, correlates at 0.998; the loudness runs alike through the intro, ScummVM's pauses longer
  by the redraw time it adds. Every one of the 66 sounds (6 songs) plays.
- **Drawing time.** The time the C64 took to draw, which ScummVM adds to each step (`DelayCalculateDelta`):
  7 ticks for each object redrawn (`markObjectRectAsDirty`, from the intrinsic state changes and
  picking up) and 0.6 for each of its strips on screen, 2 for each talking mouth flipped and 0.3 for
  each actor whose limbs moved (`processActors`), 3.6 when the room is redrawn because the camera
  moved, an object changed, or the room, lights or a load call for it (`scummLoop_handleDrawing`'s

## Phase 6: a release of its own (0.3.0-alpha)

- **Standing alone.** The host contract, screen surfaces, PNG and WAV writing, game folders, save stores, the audio sources and the SDL host came from Daventry's packages
  (0.1.0-alpha); they are now Maniacal's own, as `Maniacal.Scumm`'s `Hosting`, `Input`,
  `Graphics`, `Storage` and `Sound` and `Maniacal.Player`'s `Sdl`, only the types Maniacal uses
  (the frame scheduler, the palette type and the mixer it never used are left out). The player
  depends on SDL3 (`ppy.SDL3-CS`) directly. `Maniacal.Scumm` is optimized in Debug builds too: the
  packages had come optimized, and the per-pixel drawing compiled without optimization made the
  tests take seven times as long; with it the suite takes under a minute.
- **Packages.** `dotnet pack -c Release -o artifacts/packages` builds `Maniacal.Scumm`, the
  library (with a `.snupkg` symbol package), and `Maniacal`, the player as the `maniacal` dotnet
  tool (SDL3's Android and iOS natives left out, 13 MB). The shared metadata (version, tags,
  release notes, licence, README) is in `Directory.Build.props`; Source Link, symbols and package
  validation, which depend on `IsPackable`, in `Directory.Build.targets`. The build workflow builds,
  tests and packs every push to `main`; the publish workflow, on a tag such as `v0.1.0-alpha`,
  tests, packs and pushes to nuget.org with Trusted Publishing. Without game data the suite passes
  (each real-data test returns early), as on the CI runner. `tools/PackageSmoke/run.ps1` is the
  consumer check: from a local feed, with its own package cache, a console app plays V2, V1 and the
  C64 headless (title screen, 40,676, 43,203 and 42,752 of 64,000 pixels lit after 600 steps,
  nothing unhandled), and the tool, installed from the feed, lists V2 and takes a screenshot.
- **The first release.** `Maniacal` and `Maniacal.Scumm` 0.1.0-alpha are on nuget.org,
  published by the publish workflow from the tag `v0.1.0-alpha` through Trusted Publishing (one
  policy covers both package IDs: the tool's has no dot, so a `Maniacal.*` pattern alone misses it).
- **Three platforms.** The build workflow builds, tests and packs on Windows, Linux and macOS, for
  every push to `main` and every pull request, one platform failing not hiding how the others fare;
  publishing stays on Windows. The runners have no game data, so this checks that the engine
  builds and its own tests pass on each, not that the game plays there.

- **The public API, a first pass.** `Microsoft.CodeAnalysis.PublicApiAnalyzers` keeps the

- **The command line, ready for a 1.0.** `--help` (or `-h`) prints, on standard output, what the

## Phase 7: the NES

The NES release (1990), in English, played as ScummVM plays it, for the 1.0 if it is ready. It
runs on the version 1 interpreter, with its own resources, graphics, costumes, font, interface
and sound. `docs/nes` documents its data. The steps:

1. **The cartridge (done).** `NesRom` reads the cartridge as `ScummNESFile` does, into the DOS
   releases' room files: the index as `00.LFL` ("CF", the global objects, and where every room,
   costume, script and sound is), rooms 1 to 53 with their graphics, scripts, sounds and costumes,
   and `54.LFL` with the costume parts, the font's translation and the prepositions. Each
   resource's place and length in each of the seven ROM sets come from ScummVM's source through
   `tools/port_nes_tables.py`, and the cartridge's own lengths are checked against them. A `.prg`
   (the program data alone, as ScummVM wants it) and a `.nes` (the same behind its 16-byte iNES
   header, as dumps usually come) are both read, known by the MD5 of the program data. The index
   built from the USA cartridge is ScummVM's to the byte (`91d5db93...`, 2082 bytes), so the
   release is named as ScummVM names it, and refused for now: "the NES release is not supported
   yet". `ResourceIndex` reads the NES's index (775 objects, 80 costume slots). Tested in
   `NesRomTests`: every room file is its resources end to end, and every room, script, sound and
   costume the index names reads whole.
2. **Scripts, headless (done).** The NES runs on the version 1 interpreter with ScummVM's NES
   branches, booting and stepping without a screen (its rooms are not drawn and its actors have
   no costumes until steps 3 and 4):
   - `switchCostumeSet` takes a byte, the costume set (`NES_loadCostumeSet`); the decoder and the
     listings know it, and the world keeps the set for step 4.
   - Rooms give their width and height as words in 8-pixel units, narrow ones widened to the
     screen's 32 columns (`setupRoomSubBlocks`).
   - The camera looks through a 256-pixel-wide screen, with triggers at columns 6 and 21
     (`resetScumm`); the scripts' camera limits come from that width.
   - The title script's logo scroll waits for the camera to pass column 45, which a 256-pixel
     view never reaches: it is patched to 44 as ScummVM patches it (`applyWorkaroundIfNeeded`).
   - The clock is 60 Hz, four quarter-frames a frame, without version 1's rounding of waits to
     three ticks; the light levels are taken as they are; the talking actor is variable 41; an
     actor put in a room is not turned to the front; the security door's code is not bypassed,
     the NES having none; `setObjPreposition` changes nothing; the verbs sit a column to the right,
     in colour 1, keyed `qwer`, `asdf`, `zxcv`; and the prepositions are the cartridge's (costume
     78). The end of a cutscene follows the kid, as version 2 does.

   Tested in `NesPlayTests`: the title plays through rooms 33 and 49 to the kid selection, two
   kids picked start the game in the driveway (each kid given a CD player of his own by script
   131), with the NES's twelve verbs, and Dave walks out to the front of the house, every
   instruction handled. Left for the steps they belong to: the screen's layout (256 by 240, the
   room from line 32 to 160, the verbs and inventory under it), the narrow rooms' mouse offset
   (`_NESStartStrip`), the pickup sound (51), the NES's talk colours, the save menu's restart and
   its `Alt-F5` save script (163), and `Shift-B` to skip a cutscene.
3. **Rooms (done).** `NesBitmap` draws the NES's rooms and object images as ScummVM's `GdiNES`
   does: the pattern table of the tiles every room shares (costume 37) and the room's tileset
   after them, decoded when the room is loaded; the room's 16-colour palette, its nametable (with
   a gap of two tiles at each edge), the attributes picking a sub-palette for each 2x2 tile
   block, and the mask, a bit a column, set where a tile's pixel is not the background colour.
   An object's image patches the nametable, attributes and mask where it lies and is drawn from
   them. Without its lights a room is drawn in the dark palette, the flashlight square, on the
   NES's black (0x1D). The colours are the NES's 64, ScummVM's default NTSC palette
   (`Palettes.Nes`, from `tableNESNTSCPalette` through `tools/port_palettes.py`), which the
   world's `Palette` gives for the NES.

   The screen is the NES's, 256 by 240 (`ScreenLayout.Nes`): the room from line 32 to 160, black
   around it. The rooms 28 tiles wide (37 of the 54) show 16 pixels in from the left, cut 16 from
   the right, and the scripts' virtual mouse moves two columns left in them (`_NESStartStrip`);
   rooms change with the NES's horizontal wipe both ways (effect 6, its own 16 iterations).
   `GameWorld.Screen()` is a `Surface8` of the release's size, so the public API only grew
   `Palettes.Nes`; the engine sets the host's mode and palette from the world.

   Checked against ScummVM 2026.4.0's window: the intro's hillside matched to the pixel, the
   logo's room and the kid selection but for the text, the copyright in the verb area and the
   cursor, which later steps draw. Tested in `NesDrawingTests`: every room draws, the palette,
   the dark room, the screen's layout and the narrow rooms' place, and the intro's room as
   ScummVM showed it. The title screens ScummVM shows before the boot script
   (`playNESTitleScreens`, two pictures and the second's sparkles, `gfx_nes.cpp`) are still to
   come.
4. **Costumes and the font (done).** An NES costume (`NesCostume`) is one limb whose animations,
   `frame * 4 + direction` as elsewhere, are lists of the costume set's frames; `CostumeState`
   steps through them, back to the first after the last (`NESCostumeLoader`). The two costume
   sets, the kids' and the rest, which the scripts choose with `switchCostumeSet`, hold each
   frame's 8x8 sprites (their places, tiles, sub-palettes and mirroring), the tiles and the 16
   colours (`NesCostumeSet`, from costume slots 25 to 36). `ActorNes` animates them through
   three hooks `Actor` now has (whether the costume is ready, decoding an animation, stepping
   the animations), and `NesCostumeRenderer` draws the sprites straight onto the room's view as
   `NESCostumeRenderer::drawLimb` does: a figure facing right mirrored and 8 pixels to the left,
   a sprite crossing the view's edge left out, colour 0 not drawn, the room's mask kept in front,
   and without the light's colours the dark palette. The costume numbers' places in the sets,
   the sets' slots and the two dark palettes come from ScummVM's source through
   `tools/port_nes_costumes.py`.

   The font (`NesFont`) draws each character, 8 by 8, from the room graphics' tiles through the
   translation table in costume 77, whole and in the room's palette: the
   third sub-palette for colour 0, the fourth for 1 (`CharsetRendererNES`). The text area is the
   NES's, lines 16 to 32 on its black, the text 16 pixels in and wrapping at 256; nobody's text
   is colour 0, and the speakers' take turns between 0 and 1 (`actorTalk`'s `_NES_talkColor`).
   The message line and the verb area draw through a small glyph interface the old font also
   has, so the public `Font` is unchanged.

   Checked against ScummVM 2026.4.0's window: the whole intro, the meteor flying and the credits
   over the hillside, matched to the pixel, and the kid selection with its line of text but for
   ScummVM's cursor. Tested in `NesDrawingTests` (those screens, and the NES's animation) and
   `NesPlayTests` (the kids drawn in the driveway in their set).
5. **The interface (done).** The verb area is the NES's, from line 160 to 240 on its black,
   drawn in its font as `CharsetRendererNES` draws (whole characters, not cut at the right):
   - its twelve verbs, a column in, in colour 1 with nothing highlighted;
   - the sentence line, while any of the interface shows, from 16 pixels in, 60 characters in
     two lines of 30 (the break `drawSentence` puts after the 30th, fillers counted);
   - the inventory 48 lines down, two names a row at 16 and 152, cut at 13 characters, the last
     picked up first, the arrows the font's characters 0x7E and 0x7F between them, the down
     arrow when more than two are below (`initNESMouseOver`, `redrawV2Inventory`,
     `checkV2Inventory`);
   - the cursor, tile 0xFA of the costume set in its colours, its corner's colour left out
     (`setBuiltinCursor`).

   The NES's scripts make the object under the mouse the sentence's as the mouse passes over it
   (script 7, with `findObject`, which on the NES falls back on the inventory box under the
   mouse, its list the other way round); a click carries the sentence out. So a click somewhere
   the mouse was not is handled a step later, once the mouse has been there a step, as a
   player's mouse always is before it clicks; `Click` and `ClickObject` play the NES that way.
   Shift-B skips a cutscene, as F4 does elsewhere.

   Checked against ScummVM 2026.4.0's window: the copyright and the credits the intro spells out
   in the verb area, and the kid selection with the cursor, to the pixel (ScummVM's room wipe
   between them shows frames this does not, as with version 1's). Tested in `NesInterfaceTests`
   (the verb area, the cursor, and Dave pulling the door mat, getting the key, unlocking the
   front door with it from the inventory, opening it and going into the hall) and
   `NesDrawingTests` (those screens).
6. **Sound (done).** `PlayerNes` plays the NES's music and effects as ScummVM's `Player_NES`
   does, ticked 60 times a second among the samples: three slots, two for effects and one for
   the song, a sound of lower priority than the one in its slot left out; effects as register
   writes and waits; songs as notes started and released on instruments whose commands chain
   (`startCmd`, `releaseCmd`, `nextCmd`), the song silenced while an effect plays and given its
   channels back after. `NesApu` is ScummVM's emulation of the NES's sound chip (`APUe`): two
   square channels with their envelopes and sweeps, the triangle, the noise channel, the length
   counters and the frame sequencer, mixed at the host's rate, its integer widths kept. The
   pickup sound (51) starts at once, past the queue, as `o2_pickupObject` triggers it. The
   player's and the chip's tables come from ScummVM's source through `tools/port_nes_sound.py`;
   the title screens' twinkles wait for the title screens.

   Checked against ScummVM 2026.4.0's own output, recorded through SDL's disk audio driver and
   aligned on ours: the meteor's sounds and the title song as loud, second by second, within 1
   to 3%, their notes within ten samples of ScummVM's. Sample by sample they part where the
   chip's history does, ScummVM's having run through its title screens first: the noise
   channel's shift register, the channels' phases, and the level a stopped triangle holds (a
   constant offset, which is all of the difference late in the song). Tested in
   `NesSoundTests`: an effect played and ended, the slots' priorities, and the intro's loudness
   against ScummVM's.
7. **The walkthrough and saves (done).** The winning route plays to "You won the game!" in the
   NES release, Syd and Bernard beside Dave as on DOS, every instruction on the way handled. The
   route is DOS's but where the NES differs: there is no Unlock (the key is used with the door),
   the steel security door shuts behind a kid and is opened either way, the man-eating plant is
   "Plant" and the sealed envelope "envelope", the safe's keypad is laid out in rows of 24 pixels,
   and the kid's line on fixing the wires comes after their sound, as Dr. Fred's alarm breaks in.
   The test player clicks the NES's way: its verbs by their names (Get, Go To), its inventory the
   last picked up first, the narrow rooms 16 pixels in, the camera let come to rest before a
   click (which the NES handles a step later), and the floor sought lower where the kid stands
   at the top of the stairs.

   A save holds what ScummVM keeps for the NES: the costume set (`_NESCostumeSet`, loaded again
   whichever it is, as `loadState`'s `NES_loadCostumeSet` does), the room's view at lines 16 to
   144 (`initScreens`), the camera at the middle of 240 lines, the NES's 64 colours with no
   darkened copy and the whole shadow palette, the 8 by 8 cursor tile, and no charset loaded.
   Checked against ScummVM 2026.4.0: the route's eighteen checkpoints (`maniacnes.s31` on) load
   there and show the same screens but for the cursor and what follows the mouse there (the
   sentence line, a dark room's flashlight beam); a save ScummVM made itself, in the intro, loads
   here and plays on. Tested in `WalkthroughTests` (the route) and `NesSaveTests`: a game saved and
   restored plays on as the original, the save's NES values, and the costume set taken from the
   save.
8. **Opened (done).** `Boot` shows the NES's two title screens before its boot script, as

   square channel (`startTitleTwinkleGroup`, the channels left sounding when it ends); a click,

   nametable and attributes run-length coded, then 16 colours), a step a tick of the NES's 60th of

   The NES's own save screen, script 163, comes up on Space (ScummVM's original-menu key) and F5

   Checked against ScummVM 2026.4.0's window: both title screens and the sparkles as they came, to

enhanced DOS game, version 2, on one 720 KB floppy: `00.LFL` to `54.LFL` (ScummVM's index MD5

The steps:

1. **The disk (done).** `FatDiskImage` reads a `.st` image, the FAT12 floppy the Atari ST

   folder that holds an `00.LFL`, after the C64's disks and the NES's cartridge. The release is
   named as ScummVM names it, "Maniac Mansion (V2, English, Atari ST)" (index MD5 `0c331637...`),
   and refused for now: "the Atari ST release is not supported yet".

   The disk holds `00.LFL` to `53.LFL`, the rooms; its `54.LFL` is no room but the interpreter,
   an Atari ST program (it starts with 0x601A) that `MANIAC.PRG` runs. Rooms 1 and 10 are DOS's
   byte for byte; the index differs, and so do some rooms (53; 17 is 7,850 bytes against DOS's
   10,342), for the steps below to look into. Every
   room, script, sound and costume the index names reads as DOS's 1988 release's do (script 134
   and sounds 1, 2, 47 to 49 and 53 point at nothing whole in both), but for sound 55, whose
   length word, 10000, runs 2,232 bytes past the end of room 30: for step 3. Tested in
   `FatDiskImageTests`: files read along their cluster chains (a label, a deleted file and a
   folder among them), other disks not taken for the game, and the release's disk.
2. **Pictures and the interface (done).** The release draws in the Amiga's 16 colours, which
   ScummVM gives the Atari ST too (`resetPalette`, `tableAmigaPalette`, through
   `tools/port_palettes.py`), and public as `Palettes.Amiga`; the world's palette, the
   inspector's and a save's are those. The cursor is the ST's own picture, 16 by 16 with its
   hotspot in the middle, its marked pixels in the colour the animation is at (`setBuiltinCursor`,
   `atari_main_cursor` through `tools/port_cursors.py`), and a save keeps it so. ScummVM's busy
   cursor (`atari_snail_cursor`) shows only on its own banners, which Maniacal has none of. The
   platform comes from detection: `ResourceLoader.Platform`, ScummVM's table's, found once.
   Nothing else in ScummVM's version 2 treats the ST apart.

   Checked against ScummVM 2026.4.0's window: the copyright and the kid selection to the pixel,
   and saves made here in the driveway, on the porch and in the hall loaded there, the screens
   the same to the pixel, cursor and all (drawn where ScummVM's mouse was). Tested in
   `AtariStTests`: the colours, those screens, the cursor and what a save keeps of it, and Dave
   going into the house as on DOS.
3. **Sound (done).** ScummVM plays the ST's sounds with version 2's player (`Player_V2`), on the
   PCjr's voices by default, and so does Maniacal: the ST's sounds are the 1988 DOS release's,
   byte for byte, all but one. That one is the ending music (55): its length word says 10000 bytes,
   more than is left of room 30's file, and it is a shortened copy padded to 3 KB with `1A`
   bytes, its PC speaker part a tune of its own and its PCjr part absent. Its scripts (62, 63, 124,
   three of the eight the ST changed) load it at the end. ScummVM's loader reads the 10000 bytes
   and treats the short read as an error ("Cannot read resource"); Maniacal reads what is there,
   so the ending music plays with `--speaker` and is silent on the PCjr's voices. ScummVM
   2026.4.0 does stop there: loaded from a save made as the car leaves the garage, it ends in its
   debugger, "ERROR: (0:63:0x2D): Cannot read resource!", script 63 just past its load of the
   music (step 4).

   Checked against ScummVM 2026.4.0's own output, recorded through SDL's disk driver from a save
   made as the intro begins, loaded in both and aligned (ScummVM 820 milliseconds later): from the
   meteor (57, 58) through the music over the driveway (38), the seconds the music carries within
   about 1% as loud; where the game's own sounds come in, some differ by up to 6%. The title is
   silent in both. (Played first on DOS's PC timer rate, 236.7, the ST's sound had matched the
   recording more closely; Phase 9 put it on 240, below.) Tested in `AtariStTests`: the intro's
   loudness against ScummVM's, and the ending music on the speaker and on the PCjr.
4. **The walkthrough and saves (done).** The game is won in the ST release every way it can be,
   as on DOS (Syd's contract, Bernard's call, Wendy's memoirs, Michael's photographs), the
   routes unchanged, though the ST changed eight scripts, two costumes and seven rooms. Its
   checkpoints (`maniacst.s31` to `s58`), loaded in ScummVM 2026.4.0, show
   the same screens to the pixel, the cursor drawn where ScummVM's mouse is; a save ScummVM made
   itself loads here; a game saved here and restored plays on as the original. ScummVM cannot
   play the ST's ending (step 3); Maniacal reaches "You won the game!".

   The refusal is lifted for the release tested (index `0c331637...`); the other English Atari ST
   release ScummVM knows (`a570381b...`) is refused by name as untested. `ManiacMansion.Open`,
   `ResourceLoader.Open` and the tool open the ST from its disk image, its saves in `maniac/atari`
   (named by the platform, its release being named "V2" as DOS's is). Tested in the walkthrough
   tests (`WalkthroughTests`, `BernardsWayTests`, `WendysWayTests`, `MichaelsWayTests`),
   `SaveGameTests`, `DetectionTests` and `ManiacMansionTests`.

## Phase 9: the Amiga

The Amiga release (1988), in English, played as ScummVM plays it, for the 1.0, after the Atari
ST. It is the enhanced game, version 2, on two 880 KB floppies (`.adf`): "Maniac Disk 1" holds
the index (ScummVM's MD5 `e781230d...`) and nine rooms, "Maniac Disk 2" 45 rooms, room 44 on
both, under a `rooms` folder (ScummVM's `SearchMan.addSubDirectoryMatching(gameDataDir, "rooms")`).
The steps:

1. **The disks (done).** `AdfDiskImage` reads AmigaDOS floppy images (`.adf`), the original
   file system and the fast one: from the root block in the middle of the disk, each directory's
   hash table and chains, each file's data blocks from its header's list and its extension lists
   (the original file system's blocks with their own headers, the fast one's whole). Every `.adf`
   in a folder is read, the disks together as one folder, a file on two taken from the first,
   and the room files under `rooms` found by their own names too, as ScummVM's search path finds
   them; `GameImages.Unpack` takes them after the Atari ST's disk. The release is named as
   ScummVM names it, "Maniac Mansion (V2, English, Amiga)" (index MD5 `e781230d...`), and refused
   for now: "the Amiga release is not supported yet".

   Between them the disks hold `00.LFL` to `53.LFL`, room 44 on both and the same. The costumes
   are the 1988 DOS release's; 12 scripts and 6 rooms differ; every sound differs, in the Amiga's
   own format (step 3). Every room, script, sound and costume the index names reads as DOS's do
   (script 134 and sounds 1, 2, 47 to 49 and 53 point at nothing whole in both), but for sound 55,
   the ending music again: its entry is two bytes before the next resource, its length word
   nonsense (step 3). Tested in `AdfDiskImageTests`: two disks, one of each file system, read as
   one folder (a hash chain, an extension list, a file on both), other disks not taken for the
   game, and the release's disks.
2. **Pictures and the interface (done).** The release draws in the Amiga palette (Phase 8's).
   Its rooms change at once, with no transition, both ways: ScummVM's `fadeIn` and `fadeOut` do
   nothing for the Amiga's Maniac Mansion ("verified on WinUAE"), where DOS shows 16 frames going
   into the hall. Its cursor is a cross, 15 by 15 with its hotspot in the middle, its arms 3 to 7
   pixels out, each with an arrowhead pointing in (`setBuiltinCursor`), and a save keeps it so. Its
   clock runs at 240 quarter-frames a second, NTSC's 60 frames (`setTimerAndShakeFrequency`,
   ScummVM's default, `amiga_pal_system` off), where DOS's version 2 runs at 236.7. The verb
   colours of `vars.cpp` are version 5's (`VAR_VIDEOMODE`, which version 2 does not have), so
   nothing else in version 2 treats the Amiga apart.

   Checked against ScummVM 2026.4.0's window, from the files copied off the two disks (its
   detection wants them in a folder of their own, the `rooms` one): the copyright and the kid
   selection to the pixel, and saves made here in the driveway, on the porch and in the hall
   loaded there, the screens the same to the pixel, cursor and all. Tested in `AmigaTests`: the
   colours and the clock, those screens, the cursor and what a save keeps of it, and Dave going
   into the house with no transition, every instruction handled.

   The Atari ST runs at 240 too. ScummVM's code gives it 240, falling through to the default, and
   DOS's 236.7 is the PC's timer chip, which an ST does not have; the ST's interpreter, as the
   Amiga's, counts its 60 frames a second. Its recorded sound (Phase 8, step 3) had matched 236.7
   more closely, but SDL's disk audio driver, which made the recording, runs about 1.2% off the
   wall clock (43,554 samples a second), so the recording does not settle a 1.4% question.
3. **Sound (done).** `PlayerV2a` plays the Amiga's sounds as ScummVM's `Player_V2A` does: each
   known by the CRC of its data (from 0x0A, as long as the word at 0x08 says) and played by the
   class ScummVM wrote for it, eight at once, stepped 60 times a second among the samples. The 16
   classes Maniac Mansion's sounds use are ported (`V2aSounds`: single and looped waveforms, two
   channels left and right, pitch bends and fades, the telephone, the typewriter, the sirens, the
   exploding mansion, and the songs, played note by note on four channels with their instruments'
   samples and volume envelopes); Zak McKracken's are left out. The table of 41 sounds (CRC, class,
   arguments) comes from ScummVM's source through `tools/port_v2a_sounds.py`. Under them,
   `AmigaMixer` is ScummVM's `Player_MOD`: up to 24 channels of signed 8-bit samples, each at its
   own rate, volume and pan, a section looped or not, resampled linearly into stereo with
   ScummVM's integer arithmetic, the update called at its rate among the samples. The Amiga's is
   the one player that mixes its own two sides; the others still render mono, through an internal
   hook in `MonoAudioSource` that leaves the public API as it was. 57 of the game's 58 sounds that
   read whole are in the table (several share their data); the other, 70, is not, and ScummVM
   does not play it either ("not recognized yet").

   Checked against ScummVM 2026.4.0's own output, recorded through SDL's disk driver from a save
   made as the intro begins, loaded in both: ours is ScummVM's sample for sample, on both
   channels, at one offset, in every second checked from 20 to 57, the meteor on the right (57)
   and the song over the hillside (58); every second from 10 to 63 as loud on each side. Tested in
   `AmigaSoundTests` (the mixer's channels, loops and update, the CRC) and `AmigaTests` (the sounds
   the table knows, and the intro's loudness on each side against ScummVM's).
4. **The walkthrough and saves (done).** The game is won in the Amiga release every way it can
   be, the routes unchanged. Its checkpoints (`maniacamiga.s31` to `s58`), loaded in ScummVM
   2026.4.0, show the same screens to the pixel, cursor and all; a save ScummVM made itself loads
   here; a game saved here and restored plays on as the original. Its ending plays the intro's
   song (58), not sound 55, whose odd entry is never loaded, and ScummVM plays it through. With no
   fade-out, the ending's room 0 leaves the last room showing: "Congratulations! You won the
   game!" over the porch, as ScummVM showed it, to the pixel; Maniacal had drawn room 0 black, as
   DOS's fade leaves it, and now keeps the last room's picture there on the Amiga.

   The refusal is lifted: ScummVM knows one English Amiga release, this one. `ManiacMansion.Open`,
   `ResourceLoader.Open` and the tool open it from its two disk images, its saves in
   `maniac/amiga`. Tested in the walkthrough tests (the ending's screen in `WalkthroughTests`),
   `SaveGameTests`, `DetectionTests` and `ManiacMansionTests`.
